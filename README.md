# LunaStack（仮称）

macOSネイティブの月・惑星スタッキングソフトウェア。
AutoStakkert! のMAP（Multiple Alignment Points）方式による局所アライメントと、
RegiStax のウェーブレットシャープニングを1つのアプリに統合することを目指す。

- 対応環境: **macOS 10.13 (High Sierra) 以降 / Intel・Apple Silicon 両対応**
- 設計文書: [仕様書](docs/仕様書.md) / [実装計画書](docs/実装計画書.md)
- 現在の段階: **v0.5.0（M0〜M7＋静止画連番・カメラのRAW・キャリブレーション・仕上げ工程）/ 実機互換性検証を継続中**

---

## ⚠ パスにコロンを含めないこと

このプロジェクトは当初 `月:惑星スタックソフト`（Finder表示は「月/惑星スタックソフト」）という
フォルダ名だった。POSIXパス上のコロンはUnixビルドツールにとって区切り文字であり、
`Unix Makefiles` は `target pattern contains no '%'` で、`Xcode` ジェネレータは ZERO_CHECK で失敗した。

**2026-08-09に `LunaStack` へ改名して解決済み。**
今後このプロジェクトを移動・複製する際も、親フォルダを含めてパスにコロンを入れないこと。

## GUIアプリ

```bash
./scripts/build_app.sh
open dist/LunaStack.app
```

`dist/LunaStack.app` が常に最新の検証済みUniversalアプリである。
中間生成物は `.build/universal/` へ集約し、リポジトリ直下に別の
`LunaStack.app` を作らない。

左＝入力キューと品質グラフ、中央＝プレビュー、右＝Inspector の3ペイン構成
（⌘1 / ⌘2 で左右を畳める）。
動画または静止画連番を開く → ［品質評価］→ グラフとフレームを確認 → ［アライメント］→
参照画像と位置合わせ領域を確認 → ［スタック］→ 仕上げで追い込む → 書き出し、まで
GUIだけで完結する。各主工程は完了時に必ず停止し、次工程を勝手に実行しない。
処理後に［クリア］を押すと、入力キュー・処理結果・プレビューを空にし、
**すべての設定と仕上げのパラメータを初期値に戻す**（元動画・解析キャッシュ・書き出し済みファイル・
プリセットは残る）。アプリを起動し直したときも、入力キューと設定はすべて初期状態から始まる
（次回へ残すのは「最近使った項目」、書き出し先のフォルダ、セクションの開閉だけ）。
処理中も操作でき、中断できる。処理中にウインドウを閉じる・終了するときは確認してから中断する。

右Inspectorは4つの工程タブ（**品質評価 / アライメント / スタック / 仕上げ・出力**）で構成する。
各工程の完了後は次タブへ案内し、新しいファイルを選ぶと品質評価タブに戻る。
「どの段階の設定を触っているのか」をUIの構造で示すための分割である。
普段触らないつまみは「詳細設定」「入力の前処理」に畳んである。

**品質評価の後は、プレビュー下のスライダーを品質順に送れる。**
左端が最良のフレームで、位置ごとに「#元の番号 / 総数 · 上位 x.x% · 品質」を表示する。
並びはエンジンの上位選択と同じ規則（採用フレームを品質降順、同点は番号順、除外は最後）で、
品質グラフの「時系列 / 品質順」と連動する。グラフをクリックするとそのフレームへ移動し、
プレビュー上では ←→（Shiftで10枚、Optionで100枚）でコマ送りできる。

**選択率を変えただけの再スタックは解析をやり直さない。**
解析結果はサイドカー（`.lstk`）に、品質評価の結果は `.lstkq` に自動保存され、
次に同じファイルを開くと読み直される。
木星300フレームの実測で、解析込み 22.2 秒に対し再スタックは 2.35 秒だった。

仕上げは「RGBチャンネル合わせ → ウェーブレット（デリンギング付き）→ 色 → レベル補正（Photoshop と同じ
黒・中間・白の三角とヒストグラム、R・G・B 別も可）→ 回転・反転」の順に掛かる。切り抜きはプレビューの上で枠を描いて［切り抜く］を押すと、その場で
スタック結果が小さくなる（［元に戻す］で戻せる）。プレビューと書き出しは同じ処理系（`FinishingPipeline`）を
通すので、画面で見た結果とファイルは同じ画素になる。描画は別スレッドで行い、描いている間に
動かした分は次の1枚でまとめて描くので、ドラッグ中も途切れずに追従する。ドラッグ中も常に
本解像度で描くので、画面は「動かす前の仕上げ → 動かした後の仕上げ」とだけ移り変わる
（ウェーブレットを掛けていない画像が一瞬挟まることはない）。仕上げの表示では明るさの基準を
スタック結果に固定し、つまみを動かしても明るさが揺れない。ウェーブレットの各つまみには
－/＋ボタン（押し続けると連続）と数値欄があり、レイヤーごとに「初期値に戻す」を押せる。「仕上げ全体の効果をプレビュー」のON/OFFで
スタックそのままと、ウェーブレット欄の「ウェーブレットの効果をプレビュー」のON/OFFで
ウェーブレットだけの有無を比較できる。スタックが終わって結果を表示するときは、
位置合わせ領域の枠を自動で消す（表示メニューから戻せる）。

そのほか:

- 入力: SER / AVI（非圧縮・MJPEG）/ MOV・MP4・M4V（H.264・HEVC・ProRes など。AVFoundation で読むので、OSの版で画素が変わることがある）/ 静止画連番（TIFF・PNG・FITS・JPEG・カメラのRAW。フォルダまたは複数選択）
- 処理範囲: 大きなセンサーの一部にだけ対象が写っているときは、フレームの上で範囲を描くと、その範囲だけで
  品質評価からスタックまで行う（CLIは `--roi x,y,幅,高さ`）。範囲からはみ出すフレームがあれば知らせる
- カメラのRAW: CR2・CR3・NEF・ARW・RAF・ORF・RW2・PEF・DNG などを、すべて同梱の LibRaw 0.22.2
  （CDDL 1.0、`third_party/LibRaw`）で読む。切り抜きは機種の既定の範囲（カメラのJPEGと同じ寸法）。黒レベルを
  引いて 0..1 にするだけの**リニアのまま**で、ホワイトバランス・色変換・ガンマは掛けない
  （Bayer は色補間前の1チャンネルのまま、ほかの Bayer 入力と同じくデバイヤーする。Fuji の X-Trans は
  読み込み時に近傍平均で色補間してRGBにする）。色は仕上げの［自動ホワイトバランス］で合わせる。
  白は機種・ISOごとの飽和点（メーカーノート）を使う。撮影時刻は時差が分かるときだけUTCで使う
- 入力の前処理: フレーム範囲、Bayer配列の手動指定、デバイヤー方式（bilinear / Malvar-He-Cutler）、
  ダーク・フラット補正（動画・静止画・フォルダから全フレーム平均でマスターを作り、デバイヤー前に適用）
- プレビュー: 全体表示（小さな画像は拡大）、100%＝Retinaでも画面の実画素で等倍、
  ⌘＋ホイール・ピンチでカーソル中心のズーム、画素値の表示
- 位置合わせ領域の表示・クリックでの追加・Deleteでの削除（⌘Zで取り消し）、品質の色分けと凡例
- 品質グラフのカットラインのドラッグで参照の割合を決める（線が何に使われるかを表示）
- 詳細設定: 外れ値判定・類似度の下限・位置ずれ上限・一致度の下限・位置合わせ領域の配置しきい値・σクリップ閾値
- 除外したフレームの一覧と理由、アライメントの内訳（自動判定したモード・補間や退避の割合）
- 品質指標（勾配エネルギー／FFT周波数帯パワー比）、選択方式（割合／枚数）、輝度正規化、
  単純平均／品質重み付き平均／σクリップ、Bayerのまま合成
- 16bit TIFF、32bit float TIFF、32bit float FITS（PixInsight向け）、16bit PNGの書き出し。
  処理条件と撮影時刻（SERのタイムスタンプの中央）を記録でき、WinJUPOS形式の名前も付けられる
- 採用率を変えた複数の結果をまとめて書き出す（解析はやり直さない。既存ファイルは上書きしない）
- 残り時間とパス数の表示、完了通知
- プリセットのJSON保存（`~/Library/Application Support/LunaStack/Presets/`）
- SER診断バナーからlittle/big・12bit解釈を直接切り替え、警告を閉じる操作

バッチ処理（キューの一括処理）は v0.3.0 で廃止した。保存先は書き出しダイアログで選ぶ。

**10.13実機での動作は未検証。** ビルドは10.13ターゲットで通っているが、実行を確かめていない。
UIはmacOSの優先言語に従って日本語・英語を切り替える。

## ビルドとテスト

```bash
cmake -S . -B .build/local && cmake --build .build/local -j8
```

テストを実行する:

```bash
ctest --test-dir .build/local --output-on-failure
```

`ctest` は4つを実行する。

1. `stackcore_tests` — エンジンのユニット・リグレッションテスト（210件）
2. `gui_selftest` — 合成SERでGUIの3工程を画面の経路で通す自己検証。
   スライダーの品質順とエンジンの上位選択の一致、位置合わせ領域の当たり判定、
   編集の取り消し・やり直し、プリセットの往復、画面の仕上げと書き出しの一致を確かめる。
   GUIセッションの無い環境では `LUNASTACK_SKIP_GUI_TEST=1` で飛ばせる
3. `localization_strings_valid` — 日本語・英語リソースの構文検証
4. `availability_guard_fires` — **ビルドが失敗することを期待するテスト**。
   デプロイメントターゲット(10.13)より新しいAPIを使ったコードが
   コンパイルエラーになることを確認する。これが「成功」してしまうと
   availabilityガードが効いていない＝10.13対応が無検証、ということになる。

Universal 2（x86_64 + arm64）でビルドする:

```bash
./scripts/build_app.sh
```

出荷バイナリの最低OSを確認する:

```bash
vtool -show-build .build/universal/stackcli/stackcli
```

x86_64スライスは `LC_VERSION_MIN_MACOSX version 10.13`、
arm64スライスは `minos 11.0` になっていれば正しい
（10.14未満のターゲットでは `LC_BUILD_VERSION`/`minos` ではなく
`LC_VERSION_MIN_MACOSX` が使われる）。

## CLIの使い方

エンジンはGUIより先にCLIから完成させる方針（実装計画書 §1）。

```bash
# SERファイルのヘッダと実測値を表示（デコーダの診断用）
./.build/local/stackcli/stackcli info capture.ser

# 指定フレームをTIFFまたは16bit PNGに書き出す
./.build/local/stackcli/stackcli extract capture.ser -f 100 -o frame100.png

# 拡張子 .fits で32bit float FITSに書き出す（0.0〜1.0に正規化）
./.build/local/stackcli/stackcli extract capture.ser -f 100 -o frame100.fits

# 動画1本をスタックして1枚の画像にする（M1: グローバルのみ）
./.build/local/stackcli/stackcli stack capture.ser -o stacked.tif --top 25

# MAP局所アライメント＋オーバーラップ窓合成（M2）
./.build/local/stackcli/stackcli mapstack capture.ser -o stacked.tif --top 25 --ap-top 10
```

主なオプション:

| オプション | 説明 |
|---|---|
| `--endian auto\|little\|big` | 16bitサンプルのバイトオーダー（既定 auto） |
| `--bit-depth <N>` | 正規化に使うビット深度を上書き |
| `--float` | 32bit float TIFFで書き出す |
| 出力名 `.png` | 決定論的な16bit PNGで書き出す |
| 出力名 `.fits` / `.fit` | PixInsight等向けの32bit float FITSで書き出す |
| `--raw-cfa` | Bayerをデバイヤーせず生のCFAのまま出力 |
| `--frames <開始:終了>` | 使うフレームの範囲（1始まり、終了を含む） |
| `--bayer mono\|rggb\|grbg\|gbrg\|bggr` | 色形式を手動で指定する |
| `--debayer bilinear\|mhc` | デバイヤー方式（mhc = Malvar-He-Cutler） |
| `--dark <素材>` / `--flat <素材>` | ダーク・フラット補正（動画・静止画・フォルダ） |
| `--metadata` / `--object <名前>` | 処理条件と撮影時刻をファイルに記録する |

入力には動画のほか、静止画（TIFF・PNG・FITS・JPEG・カメラのRAW）の入ったフォルダを指定できる。
ファイル名の数字は自然順（`img2` < `img10`）に並べる。

`mapstack` のオプション（`stack` のものも使える）:

| オプション | 説明 |
|---|---|
| `--ap-size <px>` | APサイズ 32/48/64/96/128/200（既定 自動提案） |
| `--ap-top <割合>` | AP別に採用するフレームの割合（既定 10） |
| `--ap-count <枚数>` | AP別の採用枚数を直接指定 |
| `--quality gradient\|frequency` | 勾配エネルギー／FFT周波数帯パワー比 |
| `--stack-mode mean\|weighted\|sigma` | 単純平均／品質重み付き平均／σクリップ |
| `--no-normalize` | 輝度正規化を無効にする |
| `--search-radius <px>` | 局所探索の半径（既定 16） |
| `--min-score <値>` | ZNCCの下限。下回るAPは近傍から補間（既定 0.5） |
| `--ap-gradient <比>` / `--ap-level <比>` | AP採用の勾配・輝度しきい値 |
| `--ref-passes <N>` | 参照の反復精密化の回数（既定 2。1で精密化なし） |
| `--sidecar <path.lstk>` | 解析結果をサイドカーに保存する |
| `--reuse-sidecar` | サイドカーから解析結果を読み、加算だけやり直す |
| `--low-memory` | 最大RSSを抑える（1万フレームで 6105MB → 358MB、時間は約18%増） |

`stack` のオプション:

| オプション | 説明 |
|---|---|
| `--top <割合>` | 品質上位何%を加算するか（既定 25） |
| `--mode auto\|planet\|lunar` | 対象の種類（既定 auto。参照フレームの暗部の割合で判定） |
| `--min-similarity <値>` | 参照との類似度(ZNCC)の絶対下限（既定 0.5） |
| `--outlier-k <値>` | 類似度の外れ値判定の厳しさ（既定 6.0） |
| `--max-shift <画素>` | 許容する変位の上限（既定 短辺の1/4） |
| `--limit <N>` | 先頭Nフレームだけ処理する（動作確認用） |

### stack の処理の流れ

1. **全フレームの品質評価** — σ≈1のガウスぼかし後の勾配エネルギー（仕様書 §4.3）
2. **グローバルアライメント** — 惑星モードは閾値二値化＋輝度重心で粗位置を出してから位相相関、
   広視野モードは全面の位相相関。参照との類似度(ZNCC)と変位の大きさで追跡失敗を除外する
3. **加算** — 採用フレームの品質上位N%を、輝度正規化しつつ整数変位で平均する

同じ入力・同じオプションなら出力はバイト単位で再現する（加算順をフレーム番号昇順に固定）。

### 画像が破綻して見えるときの診断手順

1. `info` の **[バイトオーダー]** を見る。「ヘッダの主張と食い違っています」と
   出ていても異常ではない（キャプチャソフト間でこのフラグの解釈が割れているため
   自動判定している）。画像がノイズにしか見えない場合は
   `--endian little` / `--endian big` を明示指定して比べる。
2. `info` の **実効ビット幅** を見る。ヘッダが16bitなのに最大値が4095以下の
   右詰め12bitなら、`--bit-depth 12` を指定する（指定しないと画像が極端に暗くなる）。
   下位4bitが0の左詰めデータは既に16bitスケールなので、上書きせず16bitとして扱う。

## 検証用サンプルデータの用意

実撮影データでデコーダを確かめたいとき。`.SER` を配布しているサイトは
ほぼ無いので、AVIを落としてSERに変換する。ffmpegが必要。

```bash
mkdir -p sample-data && cd sample-data
curl -L -C - -o jupiter_pipp.avi https://jupiter-imagery.s3.amazonaws.com/2021-07-08-1050_9-Jupiter_pipp.avi
python3 ../tools/avi_to_ser.py jupiter_pipp.avi jupiter.ser --start-utc 2021-07-08T10:50:00
```

2.78GB（rawvideo bgr24 / 448x448 / 4617フレーム / 92fps）。
変換後のSERはほぼ同サイズになるので、合計6GB程度の空きが要る。
全長版（10.1GB）も同じ場所にある。

`avi_to_ser.py` は **ffmpegに画素形式を変換させない**。
グレースケール素材をrgb24で受け取ると3倍に膨らむうえ補間が入り、
CFA配列があれば壊れて、Bayer経路が検証不能になるため。
元の `pix_fmt` のまま生画素を出させ、対応するColorIDを付けるだけにしている
（`gray`→MONO、`bgr24`→BGR、`bayer_*`→対応するCFA ID）。
`has_timestamps()` を検証できるようタイムスタンプトレーラも書く。

16bit経路を試すサンプルを作る（元が8bitなので深度の中身は本物ではないが、
バイトオーダー判定の入力としては実データとして機能する）:

```bash
# AVIコンテナはgray16leを格納できない。ffmpegは警告するだけで
# rgb555leに化けたファイルを書くので、NUTを使うこと
ffmpeg -i jupiter_pipp.avi -frames:v 200 -pix_fmt gray16le -c:v rawvideo jup16.nut
python3 ../tools/avi_to_ser.py jup16.nut jup16.ser
```

全フレームを走査してmmapの挙動とスループットを測る:

```bash
c++ -std=c++17 -O2 -Ilibstackcore/include tools/ser_sweep.cpp \
    .build/local/libstackcore/libstackcore.a -framework Accelerate -o /tmp/ser_sweep
```

### M1で実装済み（入力）

- AVI（非圧縮 / MJPEG）の**自前RIFF・ベースラインJPEGデコーダ**
  - AVI 1.0 と OpenDML(AVI 2.0)。2GB超のファイルは複数の RIFF `AVIX` セグメントに分かれる
  - BI_RGB (8/24/32bit) と Y800 / GREY / Y8 / Y16 などの生画素FourCC
  - `biHeight` の符号による上下規約、行のDWORDパディング、`rec ` によるフレーム束ね
  - MJPG / JPEG / dmb1 FourCCの8bitベースライン逐次JPEG（1ch / 3ch、4:4:4 / 4:2:2 /
    4:2:0、再スタートマーカー、DHT省略時の規格既定表）
  - progressive JPEG・複数スキャン・未知の圧縮形式は**明示的に拒否**する
- SER / AVI を同じように扱う `VideoSource` 抽象。`info` / `extract` / `stack` が両対応

OS付属のデコーダ（AVFoundation）は使っていない。
「同一入力・同一設定なら全OSバージョンで同一の品質」という要件があり、
AVFoundationのAVI対応はOSバージョンで挙動が変わりうるため
主要フォーマットから排除する方針である（仕様書 §3.1・§8-7）。

### M3で実装済み

- 参照の反復精密化（仕様書 §4.4）。MAPの結果を新しい参照にして通し直す

1万フレーム（5.61GB）での実測: 最大RSS **6105 MB → 358 MB**、出力はバイト完全一致。
通常モードは既定の上限4GBを超えるので、大規模データでは低メモリモードが必須。

```bash

# 選択率だけ変えて再スタック（解析はやり直さない）

    --sidecar capture.lstk --reuse-sidecar
```

**Guizar-Sicairos DFTサブピクセル推定は実装していない。**

実測で確認したため（無ノイズ0.004〜0.010px、強ノイズでも0.039〜0.046px）。
仕様が想定していた「v1では0.1px止まり」は保守的すぎた。
詳細は[実装計画書 §6.8](docs/実装計画書.md)。

### GUIを作る過程で見つかったエンジンの不具合

**参照の反復精密化（2パス）とDrizzleを併用すると、倍率が二重に掛かっていた。**
途中パスの加算結果を次の参照にする際にDrizzleが掛かるため、2パス・2倍では
出力が4倍サイズになり、画像の左上1/4にしか中身が入らなかった。
途中パスではDrizzleを外すよう修正し、回帰テストを追加した。

既存のテストは素通りしていた（`Drizzle` クラスを直接叩いており、
パイプライン経由の多段パスを通っていなかった）。
見つけたのはGUIのAPオーバーレイである。数値だけを見るテストでは
「出力が4倍サイズ」を誰も異常だと思わない。

### v0.2.2: 疎な位置合わせ領域のタイル状アーティファクト修正

自動配置では背景や模様の乏しい場所に位置合わせ領域を置かないため、対象外周では
Hann窓の累積重みが1未満になる。従来は重みがごく小さくても局所スタック `S/W` を
100%表示し、重み0の画素だけ参照画像へ切り替えていた。この不連続が、領域サイズの
矩形として木星や月面に現れていた。

v0.2.2では累積Hann重みを支持率として局所スタックと参照画像を連続混合する。
等倍と3×Drizzleの回帰テストに加え、実写木星AVIと16bit月面SERで再検証した。
なおv0.2.1以前の`.lstk`には修正前の参照画像が保存されている可能性があるため、
サイドカー形式をv2へ更新し、古い解析結果は読み込まず再解析を要求する。

### v0.2.3: 木星の歪み・凹凸・ギザギザ輪郭を修正

木星の帯のような一方向模様では、ZNCCが高いままAPごとに別の偽ピークを選ぶ
「アパーチャ問題」が起きていた。従来の近傍補間は、偽ピーク同士を補間するため
空間的に不整合な変位場を残し、円盤と内部模様を局所的に変形させていた。

v0.2.3では各フレームのAP変位を成分別中央値で検査し、中央値まわりの散らばりが
AP間隔に対して大きすぎる場合、そのフレームだけ全APを共通のサブピクセル変位へ
安全退避する。一貫した場では孤立外れ値だけを除き、従来どおり局所変形を保持する。

木星AVI全4617フレーム・2パスでは、輪郭の楕円残差RMSが0.696pxから0.344px、
最大誤差が3.425pxから1.028pxへ低下した。月面16bit SERは安全退避0/40で、
修正前後の16bit PNGがSHA-256まで一致した。3×Drizzleも1344×1344で完走した。
旧局所変位場を再利用しないようサイドカー形式をv3へ更新したため、v2以前は再解析する。

### v0.2.4: ウェーブレット強度域を拡張

Siril 1.4.4の実装を照合すると、LunaStackと同じB3スプラインà trous分解と
`係数1＝無変化`の再構成を使う一方、Sirilの係数範囲は0〜99だった。
LunaStackはGUI上限を3に固定していたため、方式ではなく可動域が弱さの原因だった。

エンジンとCLIを0〜99、GUIを実画像で扱いやすい0〜20へ拡張した。範囲外値と
NaN/無限大は拒否する。実写木星では `8,4,2` が従来の `3,2,1` より明瞭に効き、
`16,8,3` も処理可能だった。ただし素材によってノイズとハローも増えるため、
8以上は強い設定であることを画面内に表示する。

木星外周の淡い線は、元AVIの単一フレーム、補間を使わないM1整数移動スタック、
MAP結果のすべてに同じ形で存在した。半径方向の輝度は単調に低下し、M1とMAPの
輪郭プロファイル差も中心輝度比RMS 0.00213だったため、LunaStackが作る補間
リンギングではないと判定し、円盤輪郭を変形する補正は加えていない。

| 確認項目 | 結果 |

| ffmpegとのバイト一致（実AVI） | PIPPが書いた2.78GBのAVIで、フレーム0・2000・4616が**全602,112バイト一致** |

**上下規約の罠**: 「下から上」はDIB（BI_RGB）固有の規約であり、
FourCC形式は自分で並び順を定義するので常に上から下になる。

PIPPは BI_RGB を正（下から上）で書く。
`biHeight` の符号だけで分岐した最初の実装は、Y800で上下が反転した。

### M1の受け入れ条件（2026-08-09）

同じ木星SER（4617フレーム）で `stack --top 25` を実行した結果。

| AC | 結果 |
|---|---|
| 動画1本→スタック画像がCLIで出る | **達成**。4617フレームを57秒で処理し1147枚を加算 |
| 1フレームより明確にS/Nが向上 | **達成**。惑星面の高周波残差 σ が 0.0098 → 0.00068（**14.4倍**低減）、S/N比は 24.8 → 361（**14.5倍**）。1147枚の理論上限は34倍で、その43%。整数変位しか使わないこと、シーイングでフレーム間の像自体が変わることが差の理由 |
| 追跡失敗フレームが自動除外される | **達成**。実データ中の破損フレーム30件を検出・除外した（下記）。うち10件を類似度の全域にわたって目視確認し、9件に明確な破損（テアリング、円盤の欠落、行やブロック単位の破損、横方向の継ぎ目）を確認。しきい値直上の1件（frame 2548, ZNCC 0.9924）は目視では正常と区別できなかった |
| 決定論性 | 同じ入力・同じオプションで2回実行し、出力TIFFがバイト単位で一致することを確認 |

**実データで見つかった重要な問題（対処済み）**:

このデータには横方向に引き裂かれた壊れフレームが混ざっていた。
そして**勾配エネルギーは「シャープさ」と「引き裂かれた段差」を区別できない**ため、
品質上位20フレームがすべて壊れフレームになるという事態が起きた。
当初の実装は「最高品質のフレームを参照にする」設計だったので、
よりによって壊れたフレームを基準に全体を合わせていた。

対処は2つ:

1. 参照フレームを**品質の中央値**のフレームにする。定義上ふつうのフレームであり、
   グローバルアライメントは平行移動しか求めないので参照の鋭さは推定精度に響かない
2. 参照との類似度(ZNCC)の**分布からの外れ値**を除外する。
   絶対しきい値では足りない（テアリングフレームの実測は0.72〜0.985で、
   正常フレームの0.993〜1.000との差は小さい）。中央絶対偏差を使えば明確に分離できる

**位相相関についての実測**: 純粋な位相相関（振幅を完全に捨てる）は、
視野の62%が暗背景であるこのデータで**破綻した**。全周波数の振幅を1に揃えることは、
信号がほとんど無い高周波をノイズごと増幅することを意味する。
重心が2〜4pxしか動いていないフレームに対して(37,35)のような変位を返した。
白色化を0.3に弱め、低域通過を掛けることで最大変位4pxとなり、
独立に測った重心の移動量と一致した。詳細は
[phase_correlate.hpp](libstackcore/include/stackcore/phase_correlate.hpp) の実測表。

この「最大4px」は**先頭200フレーム・参照=フレーム0での実測**であり、
動画全体の変位の上限ではない。50秒の撮影全体では像はもっと流れており、
本番実行（参照=フレーム4477）では画素あたりの加算回数が最小339／最大1147と
差が開いている。これは追尾のドリフトであって不具合ではない。

**この検証で `--min-similarity`（絶対下限 0.5）は一度も発火していない。**
実データの破損フレームを実際に捕まえたのは、すべて MAD による外れ値判定である。
絶対下限は「真っ黒なフレーム」「まるで別の対象」といった破滅的な失敗のための
最後の網であり、通常の破損検出はしない。

**既知の注意点**: 全フレーム走査時の最大RSSが2.78GBとファイル全体に達した。
mmapのページはファイルバックドで回収可能なのでリークではない。現在は
[mapped_file.cpp](libstackcore/src/io/mapped_file.cpp)で`MADV_SEQUENTIAL`を指定し、
低メモリモードでは再マップとの競合を避けるため逐次読み込みを維持している。
