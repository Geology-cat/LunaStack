# LunaStack（仮称）仕様書

**macOSネイティブ 月・惑星スタッキングソフトウェア**

- 版: 2.1
- 作成日: 2026-08-09（v2.0: Intel含む旧Mac対応に伴い技術前提を全面改訂 / v2.1: 最低OSを10.13に確定し、実際に検証可能な範囲に要件を調整）
- 対象プラットフォーム: **macOS 10.13 (High Sierra) 以降 / Intel (x86_64) および Apple Silicon (arm64)**

---

## 1. 目的と背景

### 1.1 目的

月・惑星・太陽の動画（数百〜数万フレーム）から、大気揺らぎ（シーイング）の影響を低減した高解像度静止画を生成する。AutoStakkert! の **Multiple Alignment Point（MAP）方式による局所アライメント・スタック** と、RegiStax の **ウェーブレットシャープニング** を1つのアプリに統合する。

### 1.2 背景・存在意義

- AutoStakkert! は公式にはWindows専用で、macOSではWine経由の利用となる。macOSネイティブの本格的な惑星スタッカーは事実上存在しない。
- 本アプリは **2010年頃の古いIntel MacからApple Silicon最新機まで、1つのUniversal 2バイナリで動作する** ことを差別化要素とする。天体撮影では望遠鏡制御用に旧型Macを現役運用する例が多く、旧OS対応には実需がある。

### 1.3 品質に関する最重要方針

> **スタック品質はすべての対応環境で同一とする。速度は環境に応じて犠牲にしてよい。**

- 全アルゴリズムは**CPU実装を正準（canonical）**とし、品質がGPU・OSバージョン・CPU世代に依存しない設計とする。
- GPU（Metal）による高速化は将来のオプション機能とし、有効化する場合もCPU実装と等価な結果を出すことを検証済みのものに限る（既定OFF）。
- 精度要件（サブピクセル推定精度、アーティファクト検査など §7）は**最古の対応環境を含む全環境で同一に適用**する。

### 1.4 スコープ外（v1では扱わないもの）

- 惑星の自転補正（derotation, WinJuPOS相当）
- ディープスカイ（DSO）スタック（ダーク/フラット補正を伴う長時間露光合成）
- AIベースの超解像・ノイズ除去（hallucinationのリスクがあるため方針として不採用）
- Windows / Linux 対応

## 2. 対応環境仕様

### 2.1 対応OS・アーキテクチャ

| スライス | 最低OS | 備考 |
|---|---|---|
| x86_64 | **macOS 10.13 (High Sierra)** | Metal非対応GPU機（2009〜2011年頃のMac）を含む。Xcodeの公式サポート範囲内 |
| arm64 | macOS 11.0 (Big Sur) | arm64 Macの最低OSがBig Surのため |

> **10.13を下限とした理由**: High Sierraは10.12 (Sierra) 対応の全機種にインストール可能（対応機種リストが同一）であり、下限を10.13にしてもハードウェアの切り捨ては発生しない。一方10.12はXcodeの公式デプロイメントターゲット下限（10.13）を下回るため、将来のツールチェーンでビルド不能になるリスクを抱える。**対応ハードを1台も減らさずにリスクだけを除去できる**ため10.13を採用した。

- 配布は **Universal 2 バイナリ**（x86_64 + arm64 を lipo 結合）1本とする。
- GPUは一切前提としない。プレビュー描画を含む全機能がCPUのみで動作する。

### 2.2 ハードウェア要件

| 項目 | 最低 | 推奨 |
|---|---|---|
| CPU | Core 2 Duo（High Sierra対応機の下限） | 4コア以上 |
| RAM | 4 GB | 8 GB以上 |
| ストレージ | 入力動画サイズ + 数百MB | SSD |

- x86_64コードは **SSE系までを前提とし、AVX/AVX2を無条件には使用しない**（2010年頃のCPUにAVXは無い）。vDSP等のOS提供ライブラリの内部ディスパッチに委ねる。
- 最低RAM 4GBで動作するよう、ワーキングセット上限を設定可能とする（§7）。

### 2.3 検証可能性に関する注記（実装上の重要事項）

対応環境を「宣言」することと「検証」することは別である。本プロジェクトの開発機は **Intel Mac（Core i9-9880H / macOS 15.7 / Xcode 16.4）** であり、以下の検証能力の差を仕様として明記する。

| 対象 | 検証可能な範囲 | 検証できないもの |
|---|---|---|
| x86_64 / 最新macOS | 実行・精度・性能のすべて | — |
| x86_64 / 10.13〜10.15 | 実機またはVMを用意すれば実行可能 | 環境未確保のうちは未検証 |
| arm64 | **ビルド・リンクまで**（クロスコンパイル検証済み） | 実行・精度・性能（Apple Silicon実機が必要） |

- **コンパイルが通ることは、旧OSで動作することの証明にはならない。** 弱リンクシンボルやavailability注釈付きのlibc++実装は、ビルドを通過して起動時に失敗しうる。したがって「10.13対応」の主張は**10.13実機/VMでの実行検証をもって初めて成立**するものとし、リリース条件に含める（実装計画書 §6.4）。
- ビルド時には `-Werror=unguarded-availability` を有効にし、デプロイメントターゲットより新しいAPIの使用をコンパイルエラーとして機械的に排除する。この防御が実際に機能していることを、意図的な違反コードで確認する（実装計画書 §2）。
- 出荷バイナリは `vtool -show` で `minos` の値を確認する。

### 2.4 技術スタック（対応環境から導かれる制約）

| 層 | 技術 | 10.12対応可否の根拠 |
|---|---|---|
| 処理エンジン | C++17（UIフレームワーク非依存） | クロスOSバージョンで安定。availability制約のあるlibc++機能（`std::filesystem`等）は不使用 |
| 数値計算 | Accelerate（vDSP: FFT・畳み込み、vImage） | macOS 10.0から存在。Intel/ARM両対応、OS側で最適化 |
| 並列化 | GCD（libdispatch）+ C++スレッド | macOS 10.6から存在 |
| UI | **AppKit（Objective-C++）** | SwiftUIは10.15+のため使用不可。Obj-C++はC++エンジンを直接呼べるためFFI層不要 |
| プレビュー描画 | Core Graphics（CPU描画） | Metal非対応GPU機で動作必須のため |
| 動画デコード | SER: 自前 / AVI: 自前RIFFパーサ / MOV・MP4: AVFoundation | §3.1 参照 |

**使用禁止事項**: SwiftUI、Swift Concurrency、Metal必須機能、10.13以降でのみ利用可能なAPIの無条件使用（利用する場合は実行時の存在確認と10.12フォールバックを必須とする）。

## 3. 入出力仕様

### 3.1 入力フォーマット

| 形式 | 優先度 | 備考 |
|---|---|---|
| SER v3 | 必須（v1） | 自前デコーダ。8/16bit、MONO / Bayer(RGGB,GRBG,GBRG,BGGR) / RGB、タイムスタンプ対応。リトル/ビッグエンディアン両対応 |
| AVI（非圧縮 / MJPEG） | 必須（v1） | **自前RIFFパーサ**で読む。AVFoundationのAVI対応はOSバージョンで差があり、「全OSで同一挙動」の要件を満たせないため |
| MOV / MP4 | 推奨（v1） | AVFoundation経由。OSバージョンによりデコード結果に差が出うる旨をユーザーに明示 |
| TIFF/PNG連番 | 推奨（v1.x) | フォルダ指定で連番読み込み（TIFF・PNG・FITS・JPEG） |
| カメラのRAW連番（他社） | v0.4.0 | CR3・NEF・ARW・RAF・ORF・RW2・PEF など。同梱の **LibRaw 0.22.2**（CDDL 1.0）で展開だけを行い、色補間・色変換は使わない。黒・白・切り抜きは LibRaw の値（白はメーカーノートの飽和点があればそれ）。X-Trans は近傍平均で色補間してRGBで返す。斜め配列・Foveon・CMYG は非対応 |
| カメラのRAW連番 | v0.3.3 | **自前デコーダ**。Canon CR2（ロスレスJPEG・スライス）と DNG（CFA 2×2・LinearRaw、無圧縮／ロスレスJPEG／Deflate、浮動小数点）。黒を引いて 0..1 にするだけのリニアのまま読み、CFAは1チャンネルで返してデバイヤーに任せる。切り抜きは CR2 が SensorInfo、DNG が ActiveArea＋DefaultCrop。撮影時刻は時差が分かるときだけUTCで使う。非可逆DNG・JPEG XL DNG は非対応 |
| FITS（動画/連番） | 将来（v2） | 最小実装 |

> 補足: 「同一入力・同一設定→同一品質」を全OSで保証するため、主要フォーマット（SER・AVI）はOS任せにせず自前デコードとする。
> 他社RAWに使う LibRaw はOSに依存しないCPUの整数処理なので、この要件は守られる。ただし LibRaw の版を上げると
> 機種ごとの黒・白・切り抜きの表が変わりうるため、版は固定し、上げるときは開発記録に残す。

### 3.2 出力フォーマット

- **16bit TIFF**（既定）
- **32bit float TIFF**（後処理前提の中間出力）
- PNG（8/16bit、プレビュー用途）
- **32bit float FITS**（PixInsight等との受け渡し用、正規化0.0〜1.0）
- 出力ファイル名は `元ファイル名_ap{APサイズ}_{選択率}pct_x{drizzle倍率}.tif` の規則で自動生成。

### 3.3 カラー処理方針

- Bayer入力は読み込み時にデバイヤー（v1: 高品質bilinear、v1.x: VNG/AHD相当）。
- **アライメントと品質評価は輝度（luma）で行い、得られた変位・選択結果をR/G/B全チャンネルに共通適用**する。チャンネル間で異なる幾何変換は行わない（偽色を防ぐ）。
- CFAドリズル（デバイヤーせずBayer面を直接ドリズル）はv2の研究項目。

## 4. 処理パイプライン仕様

```text
入力動画
  ↓ ①読み込み・デコード（ストリーミング）
  ↓ ②品質評価（フレーム全体）
  ↓ ③グローバルアライメント
  ↓ ④参照フレーム生成（上位N%の暫定スタック）
  ↓ ⑤位置合わせ領域の自動配置
  ↓ ⑥位置合わせ領域ごとの局所アライメント（サブピクセル）
  ↓ ⑦位置合わせ領域×フレームの品質評価と選択
  ↓ ⑧局所スタック（オーバーラップ窓合成）
  ↓ ⑨Drizzle（任意）
  ↓ ⑩後処理（ウェーブレット等・任意）
  ↓ 出力
```

全段階がCPUのみで実行される。以下、各段の仕様。

### 4.1 ①読み込み（ストリーミング2パス設計）

- 全フレームをメモリに保持しない。**パス1（解析）とパス2（スタック）の2パス構成**とし、パス間で保持するのは以下のメタデータのみ:
  - フレームごと: グローバル変位 (Δx, Δy)、全体品質スコア、平均輝度
  - AP×フレーム: ローカル変位 (Δx, Δy)、信頼度、局所品質スコア
- メタデータ量の目安: 500 AP × 10,000フレーム × 16 byte ≈ 80 MB（最低RAM 4GB機でも許容範囲）。
- SER・AVIはメモリマップドI/O（`mmap`）でランダムアクセス可能にする。MOV/MP4はシーケンシャルデコードを前提にパス設計する。
- 解析パスは縮小画像（1/2〜1/4）で行い高速化してよい（変位はスケール換算）。ローカルアライメントの最終推定は原寸で行う。

### 4.2 ②グローバルアライメント

対象全体の平行移動を推定し、以降の処理の座標系を安定させる。

- **惑星モード**: 閾値二値化＋輝度重心（centroid）で粗位置決め → 位相相関で精密化。惑星が視野内を動いても追従できること。
- **月・太陽（広視野）モード**: 縮小画像全面の位相相関。
- 推定はサブピクセル不要（整数〜0.5px精度で十分。精密化は⑥で行う）。
- 視野外にはみ出したフレーム・追跡失敗フレームは自動除外しログに記録。

### 4.3 ③フレーム全体の品質評価

- 指標: **勾配エネルギー** `Q = Σ|∇I|²`。ノイズ過敏を防ぐため軽いガウスぼかし（σ≈1）後の画像で計算する。
- 補助指標（v1.x）: FFT中〜高周波帯パワー比。UI上で指標を選択可能にする。
- 全フレームを品質降順にソートし、品質グラフをUIに表示する。

### 4.4 ④参照フレーム生成

- 品質上位N%（既定25%、範囲5〜50%）をグローバルアライメントのみで平均し、**暫定参照画像**とする。
- オプション「参照の反復精密化」（既定ON）: 暫定参照でMAP処理を1回通し、その結果を新参照として⑥をやり直す（2パス目はメタデータ再利用で高速）。

### 4.5 ⑤Alignment Point 自動配置

- APサイズ: 32 / 48 / 64 / 96 / 128 / 200 px（ユーザー選択、既定は対象サイズから自動提案）。
- **配置間隔はAPサイズの1/2（50%オーバーラップ）** の格子を基本とする。オーバーラップは⑧の継ぎ目防止の前提条件。
- 採用条件: AP領域内の平均勾配 `T = (1/N)Σ|∇I|` が閾値以上、かつ平均輝度が背景閾値以上（宇宙空間・限界外を除外）。
- 月の欠け際（明暗境界）や惑星の縁（リム）は勾配が強く出るため、**輝度マスクで対象面内に限定**する。
- 手動編集: ユーザーはAPの追加・削除・全消去が可能（UI仕様 §6）。

### 4.6 ⑥AP別ローカルアライメント

各AP i、各フレーム n について参照画像との局所変位 (Δx_in, Δy_in) を推定する。

- 相関法: **ZNCC（ゼロ平均正規化相互相関）をFFTで計算**。照度変動に頑健。
- 探索半径: ユーザー設定（既定 ±16px、シーイングに応じ±8〜±32）。
- サブピクセル推定:
  - v1: 相関ピーク近傍の**2次曲面フィット**（3×3）。目標精度 0.1px。
  - v2: **Guizar-Sicairos matrix-multiply DFT** によるアップサンプリング推定。目標精度 0.05px。
- **外れ値処理（重要）**:
  - 相関ピーク値（信頼度）が閾値未満、または変位が探索半径上限に張り付いた場合は「無効」とマークし、近傍APの変位から補間して代用する。
  - 隣接APとの変位差が物理的に不自然（例: AP間隔の1/4超）な場合は平滑化制約でクリップする。
  - 1フレーム内の有効AP変位が成分別中央値の周囲に集まらず、空間的に不整合な場合は、偽相関による対象形状の変形を避けるため、そのフレームの全APを中央値の共通サブピクセル変位へ退避する。一貫した変位場では孤立外れ値だけを除き、滑らかな局所変形を保持する。

### 4.7 ⑦AP×フレーム品質評価と選択

- AP領域ごとに勾配エネルギーで品質を評価（AP×フレームの品質行列）。
- 選択方式（ユーザー選択）:
  - **割合指定**: 各APで上位N%（既定10%、範囲1〜100%）
  - **枚数指定**: 各APで上位Nフレーム
- これにより「フレーム157は木星左上だけ採用」といった **spatial lucky imaging** が実現される。

### 4.8 ⑧局所スタック（オーバーラップ窓合成）

**本アプリの品質の核。** Delaunay三角形分割によるメッシュワープではなく、以下の方式を採用する（理由は §8 設計判断）。

```text
出力バッファ S(x,y) = 0、重みバッファ W(x,y) = 0 を用意

for 各AP i:
    for APiの選択フレーム n:
        参照座標系でAP中心 c_i に対応するフレームnの領域を
        変位 (Δx_in, Δy_in) 分シフトしてサブピクセル補間で切り出す
        窓関数 w(r)（Hann窓）を乗じて S に加算、w を W に加算
局所画像 L = S / W
参照画像 R がある場合:
    AP支持率 A = clamp(W / 1.0, 0, 1)
    最終画像 = A * L + (1 - A) * R
参照画像 R がない場合:
    最終画像 = L（未被覆は0）
```

- 窓関数はHann窓（AP中心で1、縁で0）。完全な50%オーバーラップ格子では重みの合計がほぼ1になる。自動配置で背景・低構造領域のAPが省かれた外周では重みが1未満になるため、累積重みを支持率として局所画像から参照画像へ連続的に混合する。`W > 0`なら無条件に`S/W`を100%採用してはならない（疎なAPの矩形境界が出るため）。
- サブピクセル補間: Lanczos3（v1）。
- **輝度正規化**: フレームごとの平均輝度（薄雲・透明度変動）を参照フレーム基準で正規化してから加算する。
- 加算は32bit floatで行う。**ただし「32bit floatなら誤差は無視できる」と決めつけない（要測定）**。
  0〜1正規化した値を数百フレーム加算すると、和が大きくなるにつれ1ulpも大きくなり、
  最悪ケースの平均値誤差は16bit出力の1LSB付近まで到達しうる。フレーム数が増えるほど、
  またDrizzle倍率を上げるほど悪化する。一方でfloat64アキュムレータは無条件の解ではなく、
  3×Drizzle・4Kでは出力バッファ2枚がワーキングセット上限（§7.3）を圧迫する。
  M2で「同一フレームをN枚スタックし、float32・float64・解析解を比較する」測定を行い、
  実測値に基づいて決定する（実装計画書 §3 M2）。
- オプション（v1.x）: 品質スコアによる重み付き平均、σクリッピング。

### 4.9 ⑨Drizzle

- 倍率: 1×（無効）/ 1.5× / 2× / 3×
- カーネル: Square（pixfrac可変、既定0.9）。Gaussian はv2。
- ⑧の枠組みを流用し、出力グリッドを拡大して各画素をサブピクセル変位込みで投影する（S/Wの2バッファ方式はそのまま）。
- UI上に注意書きを表示: 「Drizzleが有効なのはアンダーサンプリング時のみ。焦点距離が十分長い場合は解像度は向上しません」。
- 高倍率Drizzleはメモリ使用が増えるため、低RAM機ではタイル分割処理でワーキングセット上限内に収める。

### 4.10 ⑩後処理

スタック結果に対する非破壊編集（元スタックは保持し、パラメータのみ保存）。

#### ウェーブレットシャープニング（RegiStax風）

- **à trous（undecimated）ウェーブレット**で6レイヤーに分解。ダウンサンプリングしないため位置不変で、天体シャープニングに適する。
- 分解: `c_0 = I`, `c_j = h_j * c_{j-1}`（B3スプラインカーネル、穴あき拡張）, `w_j = c_{j-1} - c_j`
- 再構成: `I' = R + Σ g_j·w_j`
- レイヤーごとのパラメータ: **Sharpen係数 g_j（エンジン0〜99、GUI実用域0〜20）** と **Denoise（soft-threshold、0〜1）**。`g_j=1` は無変化であり、素材に応じて細かい層から上げる。8以上はノイズやハローも増幅しやすいため画面内で注意を示す。
- 実装はvDSPの分離可能畳み込み（CPU）。プレビューは選択領域（既定512×512）で更新し、目標応答は §7 の性能要件に従う（推奨環境 <100ms / 最低環境 <500ms）。

#### その他の後処理（優先度順）

| 機能 | 版 |
|---|---|
| ヒストグラムストレッチ（黒点/白点/ガンマ） | v1 |

## 5. 機能仕様（パイプライン以外）

### 5.1 バッチ処理

- 複数の入力ファイルをキューに登録し、同一設定で連続処理できる（AutoStakkert!の実用上の強みであり必須機能）。
- 処理設定は**プリセット**として保存・呼び出し可能（JSON、`~/Library/Application Support/` 配下）。
- 低速な旧型機では長時間バッチが前提となるため、**キューの途中中断・再開**（処理済みファイルのスキップ）に対応する。

### 5.2 解析結果の保存

- 解析パスの結果（変位・品質メタデータ）をサイドカーファイル（`.lstk`、独自バイナリまたはJSON+バイナリ）に保存し、パラメータ変更時（選択率変更など）に解析をやり直さず再スタックできる。旧型機ほど解析の再利用価値が高い。

### 5.3 ログ・再現性

- 処理パラメータ一式を出力TIFFのメタデータおよびサイドカーに記録する。
- **同一マシン・同一入力・同一設定で出力がビット一致**すること（決定論性）。
- Intel / Apple Silicon 間では浮動小数点演算順序の差による微小差を許容するが、品質指標（合成データに対するRMS誤差・PSNR/SSIM）が**両アーキテクチャで同一の合格基準を満たす**ことをテストで保証する。

## 6. UI仕様

AppKit（Objective-C++）による3ペイン構成。描画はCore Graphics（CPU）で行い、GPUを前提としない。

```text
┌────────────┬──────────────────────┬───────────────┐
│ 左: 入力    │ 中央: プレビュー       │ 右: Inspector │
│ ・ファイル   │ ・フレーム表示         │ ┌ Align      │
│   キュー    │ ・AP表示/編集         │ ├ Quality    │
│ ・フレーム   │ ・スタック結果         │ ├ Stack      │
│   一覧     │ ・ズーム/パン          │ ├ Drizzle    │
│ ・品質      │                      │ ├ Wavelet    │
│   グラフ    │                      │ └ Export     │
└────────────┴──────────────────────┴───────────────┘
```

- 品質グラフ: 横軸フレーム番号（時系列）と品質順ソートの切替。選択率のカット位置を可視化。
- APオーバーレイ: 自動配置結果を表示し、クリックで追加、右クリック/Delで削除。
- 進捗表示: パス別（解析/スタック）のプログレスバー、キャンセル可能。残り時間の推定表示（旧型機での長時間処理に配慮）。
- プレビューのズーム/パンはタイル化したCGImageキャッシュで実装し、最低要件機でも操作に追従すること（60fpsは要求しない。目標: 操作から表示更新まで<100ms）。
- UI言語: 日本語・英語。

## 7. 性能・品質要件

### 7.1 品質要件（全環境共通・妥協しない）

| 項目 | 要件 |
|---|---|
| アライメント精度 | 合成テストデータ（既知変位）で RMS誤差 v1: ≤0.1px、v2: ≤0.05px。**全対応環境で同一基準**（測定はx86_64で実施） |
| アーティファクト | 一様輝度領域・AP境界に格子状パターンが視認されないこと（差分画像・FFTピーク検査で検証） |
| 決定論性 | 同一マシン・同一入力・同一設定で出力がビット一致。最適化フラグは `-O2` 固定とし、`-ffast-math` / `-Ofast` を使用しない。スタック加算のリダクション順序を実行ごとに変えない |
| アーキテクチャ間等価性 | 品質基準はarm64にも同一に適用する。ただし**arm64での測定はApple Silicon実機を確保するまで実施できない**ため、現状はビルド・リンク検証のみ。実機確保時に精度回帰スイートを実行することをリリース条件とする（§2.3） |

### 7.2 性能要件（環境ごとの参照目標。品質と異なり環境で変わってよい）

基準ジョブ: 3,000フレーム・800×600・16bit・AP約200個の解析＋スタック合計。

| 環境ティア | 想定機 | 目標時間 | ウェーブレットプレビュー(512×512) | 位置づけ |
|---|---|---|---|---|
| 推奨（Apple Silicon） | M2クラス | 3分以内 | <100ms | **参考値**（実機未確保のため測定不能） |
| 開発基準（Intel 8コア） | Core i9-9880H | 5分以内 | <150ms | **AC（開発機で必ず測定）** |
| 中位（Intel 4コア） | 2015年頃 i5/i7 | 10分以内 | <200ms | 環境確保できれば測定 |
| 最低（Core 2 Duo） | 2010年頃・RAM 4GB | 40分以内（完走すること） | <500ms | **参考値**（実機未確保。確保できた場合のみAC化） |

> 受け入れ条件（AC）として拘束力を持つのは、実機で測定できるティアのみとする。測定機のないティアは設計上の参考値として扱い、「達成した」と記載しない。実機が確保できた時点でACへ格上げする。

### 7.3 リソース要件

| 項目 | 要件 |
|---|---|
| 対応規模 | 30,000フレーム / 4K解像度まで（ストリーミングでメモリ上限を超えない） |
| メモリ上限 | ワーキングセット既定4GB以下。**設定で2GBまで引き下げ可能**（低RAM機向け。タイル分割・キャッシュ縮小で対応し、品質には影響させない） |

## 8. 主要な設計判断とその理由

本仕様はChatGPTとの検討ログ（アルゴリズム構成の大枠）をベースに、以下の点で判断を確定・変更した。v2.0では対応環境要件の拡大に伴い 2. と 7. を全面改訂した。

1. **局所スタック統合: メッシュワープではなくオーバーラップ窓合成**
   検討ログではDelaunay三角形分割＋アフィン補間が第一候補だったが、三角形境界で変形の1次微分が不連続になり継ぎ目が出やすい。50%オーバーラップ格子＋Hann窓の加重合成は継ぎ目を構造的に排除でき、「AP別に採用フレームが違う」spatial lucky imagingとも自然に整合する。メッシュワープ（dense変位場）はv2以降の研究項目とする。

2. **技術スタック: C++17エンジン + Objective-C++/AppKit UI**（v2.0で改訂）
   v1.0ではSwift単一言語（SwiftUI + Metal）を採用していたが、旧Mac対応要件によりSwiftUI（10.15+）・Swift Concurrency（10.15+）・Metal前提（10.13はMetal非対応GPU機を含む）がすべて使用不可となったため撤回。C++17エンジンはOSバージョン依存が最小で、Objective-C++のUIからFFI層なしで直接呼べる。数値計算はvDSP（macOS 10.0から存在、Intel/ARM両対応）に集約する。

2b. **最低OSを10.12ではなく10.13とする**（v2.1で決定）
   §2.1の注記のとおり、対応ハードウェアを1台も減らさずにツールチェーンリスクを除去できるため。

2c. **検証できないことをACに書かない**（v2.1で追加）
   開発機がIntel専用であることから、arm64実行検証・Apple Silicon性能測定・Core 2 Duo級の性能測定は現時点で不可能である。これらを「参考値」と「AC」に明確に分離し、未検証のものを達成済みと記載しない方針を仕様に組み込んだ（§2.3・§7.2）。

3. **CPU実装を正準とし、品質をハードウェア非依存にする**（v2.0で追加）
   「速度は犠牲にしてよいが品質は落とさない」という要件を、「品質を決めるコードパスはCPU実装ただ1つ」という形で構造的に保証する。GPU加速を将来追加する場合も、CPU実装との等価性検証を通過したものだけを既定OFFのオプションとして提供する。

4. **アライメントへのAI不使用**
   検討ログの結論に同意。0.05〜0.1px精度・数万フレーム・hallucination不許容という条件では古典的相関法が優位。

5. **2パスストリーミング設計の明文化**
   数万フレームを扱う以上、メモリ設計はアルゴリズムと同格の主要仕様である。RAM 4GBの旧型機対応でこの設計の重要性はさらに増した。

6. **外れ値処理・輝度正規化・参照反復の追加**
   実データ（薄雲、低コントラストAP、突発的な揺らぎ）で品質を左右するのはこれらの泥臭い処理であり、v1から仕様に含める。

7. **主要入力フォーマット（SER・AVI）の自前デコード**（v2.0で改訂）
   「全OSバージョンで同一挙動・同一品質」を保証するため、OS付属デコーダ（AVFoundation）への依存を主要フォーマットから排除する。AVFoundationはMOV/MP4の補助経路としてのみ使用し、OS差の可能性をユーザーに明示する。

8. **Drizzleの適用条件をUIで明示**
   オーバーサンプリング済みデータに3×Drizzleをしても情報は増えない、という検討ログの指摘をユーザー向け注意書きとして製品に反映する。

## 9. 用語集

| 用語 | 意味 |
|---|---|
| AP (Alignment Point) | 局所アライメントの単位となる小領域（32〜200px角） |
| MAP | Multiple Alignment Points。多数のAPで局所変位を推定・補正する方式 |
| ZNCC | ゼロ平均正規化相互相関。照度変動に頑健な類似度 |
| 位相相関 | FFTの位相差から平行移動量を求める手法 |
| spatial lucky imaging | フレーム単位でなく局所領域単位で良像を選択する考え方 |
| Drizzle | サブピクセル変位を利用して高解像度グリッドへ再構成する手法（Fruchter & Hook 2002） |
| à trous wavelet | ダウンサンプリングしない多重解像度分解。位置不変でシャープニング向き |
| SER | 天体撮影用の非圧縮動画コンテナ形式 |
| Universal 2 | x86_64とarm64の両コードを1つに束ねたmacOSバイナリ形式 |
| 正準実装（canonical） | 品質の基準となる唯一の実装。他実装（GPU等）はこれとの等価性で検証される |
