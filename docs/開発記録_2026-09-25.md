# LunaStack 開発記録（2026-09-25 / v0.3.0）

作成: Claude Code。2026-09-25 以降、GUI・エンジンとも Claude Code が実装する
（以前の「エンジンは Codex」という分担は廃止）。

改善候補の洗い出し（B=不具合 / U=使い勝手 / F=機能 / P=性能 / M=保守）のうち、
F5（低メモリモードの自動判定）を除くすべてと、次の要望に対応した。

- 「すべて処理」（バッチ処理）を廃止する
- 「仕上げ・出力」の出力先指定を廃止する（保存先は書き出しダイアログで選ぶ）
- 品質評価の後、フレームのスライダーを品質順に送れるようにし、位置ごとに上位何%かを出す
- 静止画連番（複数の静止画）を入力にできるようにする

---

## 1. 要望への対応

| 要望 | 対応 |
|---|---|
| バッチ処理の廃止 | 「すべて処理」、⌘B、キュー右クリックの「このファイルだけ処理」（一括経路を通っていたため工程ごとに止まらなかった）、バッチ用の自己検証モードを削除 |
| 出力先指定の廃止 | 仕上げ・出力タブの出力先欄を削除。書き出しダイアログは前回のフォルダを覚える |
| 品質順のフレーム送り | 品質評価の完了で自動的に品質順へ。表示は「#元の番号 / 総数 · 上位 x.x% · 品質 q」、除外フレームは理由を表示。並びはエンジンの `select_top_frames` と同じ規則（採用フレームを品質降順、同点は番号昇順、除外は最後）。品質グラフの「時系列 / 品質順」と連動 |
| 静止画連番 | TIFF・PNG・FITS・JPEG。フォルダを落とすか複数の画像を選ぶと1本の連番になる（自然順） |

### 最終レビューで見つけて直したもの

- 範囲の数値欄やポップアップに触れただけ（値は変えない）でも入力を開き直し、スタック結果と
  仕上げを捨てていた。開いたときの読み方の指紋と比べ、変わっていなければ何もしない
  （自己検証 `selfCheckUntouchedInputKeepsResult` を追加）
- フレーム範囲が別のファイルや次回の起動へ引き継がれ、短い動画が「範囲が空」で開けなくなっていた。
  範囲はファイルごとのものとし、別のファイルを選ぶと空欄に戻す（解析済みならサイドカーから戻る）。
  起動時の復元とプリセットの適用では範囲を持ち込まない
- まとめて書き出しが「いまの」Drizzle倍率で作り直していた。表示中の結果を作ったときの倍率・pixfracに揃える
- フレーム情報の「上位 x.x%」を先頭に置き、最低幅を確保した（最小幅の英語UIで切り詰まっていた）

## 3. 設計上の要点

- **入力はすべて `open_video` を通す。** 前処理（範囲・色・補正）はその内側のラッパーで掛かるので、
  パイプラインの関数は前処理を知らない。前処理が既定値なら元のソースをそのまま返す
- **補正はデバイヤー前のCFAに掛ける。** フラットはBayerの2×2位相ごとに正規化する
  （全体で割ると色ごとの感度差まで「補正」してしまう）
- **仕上げは `FinishingPipeline` 1つを通す。** CLI・GUIのプレビュー・書き出し・まとめて書き出しが同じ処理系
- **メタデータに現在時刻を入れない。** 撮影時刻は入力（SERのタイムスタンプ）由来
- サイドカーの指紋に補正の素材・前処理・詳細設定を加えた。前の版の `.lstk.json` とは指紋が合わないので、
  v0.3.0 で初めて開いたファイルはアライメントからやり直しになる（安全側）

## 7. v0.3.2（ウェーブレット仕上げの改善）

| 要望 | 原因と対応 |
|---|---|
| スライダーを動かすとプレビューが途切れる | **原因**: 描画要求のたびに番号を進め、描き上がった結果の番号が古ければ捨てていた。ドラッグでは描画より速く要求が来るため、ドラッグ中の結果がすべて捨てられて画面が止まり、指を止めた瞬間に飛んでいた（ドラッグを模した自己検証で、60回の操作に対し更新0回を再現）。加えて「表示を明るくする」が1枚ごとに範囲を測り直すので明るさが揺れ、大きな画像では半分の大きさの下書きをそのまま出していた。**対応**: 描画中の要求は1つだけ控えて最新の設定ですぐ次を描く、結果をランループへ共通モードで渡す、明るさの基準をスタック結果に固定する、下書きは元の大きさに戻して出す。更新回数は 448×448 で60回中61回、1920×1200 で26〜27回（縮小版で約26コマ/秒）になった |
| ＋/－ボタンでの微調整（押しっぱなし可） | 各つまみ（強調・ノイズ・連動の強さ・輪抑制）に－/＋を付けた。押し続けると連続し、長く押すほど1回の変化が大きくなる |
| 数値の入力 | 数値欄を直接編集できるようにした。全角の数字も読み、範囲外は収め、読めない値は元に戻す |
| 各レイヤーに「初期値に戻す」 | レイヤーの見出しの右に置いた（強調1.00・ノイズ0.00） |

自己検証を追加した: ドラッグ中の連続更新（10回以上/秒）、－/＋・数値入力・レイヤーの初期化。
木星AVI・太陽SER（1920×1200）・月面SERで合格。

## 8. v0.3.3（ちらつき・RAW・設定パネルの横ずれ）

| 要望 | 原因と対応 |
|---|---|
| つまみを動かした瞬間に、ウェーブレット未処理の画像が一瞬見える | **原因**: ドラッグ中（±ボタンの押し続けも含む）は、大きな画像か直前の描画が80msを超えると半分の解像度の下書きを出していた。半分の解像度ではレイヤーを1段ずらして当てるので**最も細かいレイヤー1の効果が消え**、元の大きさに拡大し直すとぼやけるため、未処理のように見えていた。**対応**: 下書きをやめて常に本解像度で描く。そのぶん速くするため、(1) 仕上げの各工程（分解・再構成・デリンギング・色・ストレッチ・形）を行単位で並列化（画素ごとの演算順は変えないので結果は一致）、(2) 再構成を `I + Σ(g_j·w'_j − w_j)` に書き直し、初期値から変えたレイヤーだけを読む、(3) デリンギングの許容範囲（元画像の近傍の最小・最大）を使い回す、(4) 途中の画像と出力先を使い回す、(5) 画面用の8bit画像と縮小段を描画と同じ裏のスレッドで作り、縮小段は自前の2×2平均で並列に作る。6240×4160 のカラーで仕上げ1回が 3.7秒 → 約0.13秒、メインスレッドの負担は1回0.44秒 → ほぼ0になった |
| リニアなRAW（CR2・DNGなど）への対応 | 自前のデコーダを書いた（`raw_reader`・`lossless_jpeg`）。**Canon CR2**: ロスレスJPEG（SOF3）を展開してスライスの並びを戻し、メーカーノートの SensorInfo で遮光部を除いた範囲（6D Mark II なら 6240×4160）を切り抜く。黒は左の遮光部の平均（Bayerの位相ごと）、白は記録ビット数の最大値。**DNG**: RAW の IFD（SubIFD も探す）から、CFA（2×2）と LinearRaw を、無圧縮（詰めた10/12/14bit・浮動小数点を含む）・ロスレスJPEG・Deflate（予測子つき）で読み、LinearizationTable・BlackLevel（繰り返し・行列差分）・WhiteLevel・ActiveArea・DefaultCrop を反映する。CFAPattern は ActiveArea の左上から数える。どちらもホワイトバランス・色変換・ガンマは掛けずリニアのまま 0..1 にし、CFA は1チャンネルのまま既存のデバイヤー・ダーク/フラット補正に渡す。撮影時刻は EXIF の日時に時差（OffsetTimeOriginal か Canon の TimeInfo）を足してUTCにし、連番の全部にそろえば中央時刻・DATE-OBS に使う。CR3・NEF・ARW・RAF・非可逆DNG・JPEG XL DNG は非対応（はっきりエラーにする） |
| 設定パネルがトラックパッドの横スワイプで左右に動く | 横スクロールバーと横の弾性を切り、表示範囲の原点 x を常に0に固定するクリップビュー（`VerticalClipView`）にした。中身の幅はスクロールビュー全体ではなく表示領域の幅に合わせる |

再構成の式を変えたので、同じ設定でも書き出しの画素が v0.3.2 と最大 2×10⁻⁷ 程度（float の丸め）違う。
同じ版の中では、同じ入力・同じ設定から同じ出力になる（2回書き出してハッシュ一致を確認）。
並列化だけの段階では v0.3.2 とバイト単位で一致することを確かめてから式を変えた。

自己検証を追加・強化した:
- 連続プレビュー: 更新回数に加え、強調を上げていく操作の途中で画面の高周波の量が一度も下がらないこと
  （＝強調の無い画像が挟まらないこと）を見る。6240×4160 でも合格
- 設定パネル: 横スクロールを送っても、直接ずらそうとしても横位置が0のままであること

RAWの検証:
- EOS 6D Mark II の CR2 3枚で、切り抜く前の生の値が LibRaw（Homebrew版、照合にだけ使いアプリには組み込まない）と
  26,966,016 画素すべて一致。黒は 2048.1 前後（LibRaw は 2048）。1枚の展開は約0.37秒
- 手元の DNG: 無圧縮 LinearRaw（16bit）・iPhone 14 Pro の ProRAW（ロスレスJPEG・10bit・線形化表）は
  LibRaw と正規化後の差 3×10⁻⁸ 以下、Kiss X3 由来の16bit浮動小数点 Deflate は LibRaw の整数化の丸め幅（6×10⁻⁵）以内。
  JPEG XL の DNG は「非対応」のエラーになる
- CFA の DNG は手元に無いので、`tests/data/make_raw_fixtures.py` で作った試験画像（16bit無圧縮・ロスレスJPEGタイル＋SubIFD・
  詰めた12bitビッグエンディアン＋線形化表＋黒の行列差分・LinearRaw浮動小数点）と小さな CR2（スライス分割あり）で単体テストにした。
  CFA の並びの起点（ActiveArea の左上）は LibRaw の読み方と一致することを確かめた
- GUI: CR2 8枚（6240×4160）の連番で品質評価 → アライメント → スタック → 仕上げの自己検証が合格。
  スタック結果はホワイトバランス前なので緑がかる（仕上げの［自動ホワイトバランス］で合わせる）

最終確認で直したもの:
- 仕上げの描画を頼んだ時点でプレビューの明るさの対応（黒点・白点のON/OFFなど）を変えていたため、
  描き上がるまでの間、前の画像だけ明るさが変わって一瞬ちらついた。要求時は対応を計算するだけにし、
  結果と同時に差し替えるようにした（自己検証「表示の対応」を追加）
- RAW と JPEG を同時に保存したフォルダでは、連番に両方が混ざって途中で形式が食い違った。
  RAW があれば RAW だけ、無ければいちばん多い形式だけを使う（`select_sequence_files`）

既知の制限:
- CR2 の白は記録ビット数の最大値（16383）にしているので、実際に飽和した画素（6D Mark II の ISO1250 で
  約11301）は 0.65 前後になる。露出オーバーでなければ影響しないが、飽和した部分はホワイトバランス後に色が付く
- 6240×4160 では仕上げが数GBのメモリを使う（6層の詳細が各約300MB）。大きな画像は切り抜いてから仕上げると軽い

## 9. v0.4.0（他社のカメラRAW・LibRaw の同梱）

利用者と相談して、CR3・NEF・ARW・RAF などは **LibRaw を同梱して読む**ことにした（CR2・DNG は検証済みの自前デコーダのまま）。

| 項目 | 内容 |
|---|---|
| 同梱 | LibRaw 0.22.2 を無改変で `third_party/LibRaw` に置き、静的ライブラリとしてビルドする（-O2・-fno-fast-math・10.13 の availability 検査つき。約11秒）。入手元・SHA-256 は `README.LunaStack.md` |
| ライセンス | LGPL 2.1 / CDDL 1.0 の選択制のうち **CDDL 1.0** を選んだ。アプリ本体のライセンスには及ばない。アプリの Resources/ThirdParty/LibRaw に LICENSE.CDDL・COPYRIGHT・入手方法を入れる |
| 使い方 | `open_buffer`（メモリに割り付けたファイル）→ `unpack` → `raw2image_ex(1)`（見える範囲を切り出しつつ、dcraw_process と同じ方法で黒を引く）。色補間・色変換・ガンマ（`dcraw_process`）は使わない。白は黒を引いた後の maximum、メーカーノートの線形の上限（linear_max）があればそちら |
| 並び | Bayer は `COLOR()` から2×2の並びを求めて1チャンネルで返す。Fuji の X-Trans（6×6）は、無い色を近傍（3×3、無ければ5×5）の同じ色の平均で埋めてRGBで返す（線形の平均だけなのでリニアのまま） |

| CR2 の白 | 記録ビット数の最大値（16383）から、LibRaw がメーカーノートから読む ISO ごとの飽和点に変えた（6D Mark II の ISO1250 で 11301）。飽和した画素がちょうど 1.0 になる |

検証（raw.pixls.us の CC0 サンプル。作業用フォルダに置き、リポジトリには入れない）:

## 10. v0.4.1（カメラRAWを LibRaw に一本化）

利用者の判断で、CR2・DNG も自前のデコーダをやめて LibRaw で読むようにした（`raw_reader.cpp` は拡張子の判定と
EXIF の日時の計算だけになり、自前のロスレスJPEGデコーダ・CR2・DNG の読み込みは削除）。

- 切り抜きは LibRaw の `raw_inset_crops[0]`（CR2 の SensorInfo・DNG の DefaultCrop・各社の既定の範囲）。
  カメラの JPEG と同じ寸法になる（6D Mark II 6240×4160、α7 III 6000×4000、D850 8256×5504、E-M1 Mark II 5184×3888）。
  LibRaw は Bayer の並びを保つため、切り抜きの左上を偶数の位置に寄せることがある
- Deflate の DNG（浮動小数点・HDR）のため LibRaw を `USE_ZLIB` 付きでビルドし、macOS 標準の libz をリンクした
- 浮動小数点の DNG は、LibRaw が整数へ直すとき白を超える値があると画像ごとの最大値で縮めるので、DNG の WhiteLevel に
  同じ倍率を掛けた値を白にした（連番の中で明るさの基準が1枚ごとに変わらないように）
- LibRaw の既知の近似: BlackLevelDeltaH/V（列・行ごとの黒の差分）は平均を黒に足すだけ。黒が位相ごとに違うときは、
  位相ごとの黒を引いたあと共通の黒を引いた白で割る
- 前の版（自前デコーダ）との比較: 6D Mark II の CR2 は同じ範囲・同じ並びで、値の差は最大 5×10⁻⁶（黒 2048.1 と 2048 の差）。
  iPhone SE の DNG（ロスレスJPEG・CFA）は 4×10⁻⁸
- 試験画像（`tests/data/raw_*.dng`）は ActiveArea と DefaultCrop を偶数にして作り直し、CR2 の小さな試験画像は削除した
  （LibRaw は機種の表で CR2 を読むので、架空の機種の CR2 は読めない。実機の CR2 で確かめている）
- 自己検証の「連続プレビュー」は、400万画素を超える画像では「ドラッグ中に2回以上更新される」を基準にした。
  6240×4160 のカラーはこの Mac（メモリ16GB）で仕上げ1回に0.1秒以上かかり、メモリの込み具合で毎秒3〜8回と揺れて、
  10回の基準を割ることがあったため。強調の無い画像が挟まらないことの検査は毎回合格している。
  大きな画像はウェーブレットの分解だけで約2GBを使うので、メモリを減らす工夫は今後の課題

## 14. v0.5.0（窓合成の読み方の作り替え・MOV/MP4）

### 窓合成を「フレームごとに1回読む」順にした
以前は位置合わせ領域（AP）ごとに、選んだフレームを読み直していた（読み込み・色補間が AP×フレームの回数）。
- `WindowedStacker` に AP ごとの足し込み（`Ap`・`start_ap`/`accumulate`/`commit_ap`）を独立して持つ口を足した。
  別々の `Ap` への `accumulate` は同時に呼べる。従来の `begin_ap/add_frame/end_ap` はこの上に載せた
- `map_stack_pass` は、AP の足し込みを同時に持てる上限（物理メモリの1/8、256MB〜2GB）で AP を番号順の組に分け、
  組ごとにフレームを番号順に1回だけ読み、そのフレームを選んだ AP へ並列に足す。確定は AP 番号の昇順
- 1つの AP の中ではフレーム番号の昇順に足し、確定は AP 番号の昇順なので、加算の順序は以前と同じ。
  モノクロ・カラー、平均・重み付き・σクリップ、ドリズル 1.5/2倍、CR2 の全体・処理範囲、木星AVI全フレームで、
  出力がバイト単位で一致することを確かめた
- v0.4.3 で入れた窓合成の中の控え（`PreparedFrameCache`）は不要になったので外した
- 再スタックだけの時間: 木星AVI（全フレーム）93秒 → 5秒。CR2 8枚（6240×4160）は約12秒で同程度

### MOV・MP4 の読み込み（AVFoundation）
- エンジンに `movie_source.mm`（Objective-C++・MRC）を足し、`open_video` が MOV・MP4・M4V を開けるようにした。
  GUI（追加・ドロップ・開くパネル・Info.plist）と CLI（`info` を含む）も対応
- 開くときに、圧縮のままのサンプルを走査して表示時刻の表を作る（デコードしない）。**編集リストを反映した表示時刻
  （Output PTS）を使う**こと、**サンプル数0の目印のバッファを数えない**こと、トラックの表示範囲の外を除くことが要点
  （どれかを外すと、Bフレームつきの H.264 でフレーム数や番号がずれた）
- 番号順に読まれる限りはデコーダを進め、少し先を頼まれたら途中を最大256MB控え、離れた番号だけその位置から読み直す
  （並列のワーカーが番号を前後して取りに来ても読み直さない）。前処理まで済ませたフレームは静止画連番と同じく控える
- 撮影時刻: QuickTime の作成日時（`mdta/com.apple.quicktime.creationdate`）に時差が書かれていれば、各フレームの
  表示時刻を足して UTC にする。ffmpeg の `-metadata` は iTunes 形式の欄に入るので、試験画像は AVFoundation で書いた
- 試験: 64×48・30フレームで明るさがフレーム番号を表す動画（H.264 Bフレームつき MP4・ProRes MOV・作成日時つき MOV）を
  `tests/data/make_movie_fixtures.sh` で作り、番号順・ばらばらの順とも正しいフレームが出ること、フレーム範囲・処理範囲、
  撮影時刻を単体テストにした。木星AVI（4617フレーム）を H.264 MP4・HEVC MOV にしてスタックすると、AVI からの結果と
  PSNR 44〜46dB（相関0.9993）で一致。GUI の自己検証も MP4 で合格

最終確認で直したもの:
- MOV・MP4 は OS の版で画素が変わりうることを、GUI の警告バナーでも知らせるようにした（仕様書 §3.1「ユーザーに明示」）
- 1GB級の動画（4K・60fps・60秒、915MB・3600フレーム）は、開くたびのフレーム表づくりに0.5〜1.8秒かかった。1回の作業で
  何度も開くので、パス・大きさ・更新時刻をキーにプロセス全体で使い回すようにした（2回目以降 0.003秒）
- 読み進めて追い越したまま頼まれなかったフレームの控えを捨てるようにした（飛ばして読む工程で上限を使い切らないように）
- 低メモリモードでは、窓合成で同時に持つAPの足し込みを256MBに抑える（組の数が変わるだけで出力は同じ。単体テストで
  1組・APごと・低メモリの結果がビット一致することを確認）

既知の制限: 縦長で撮ったスマートフォンの動画は回転の情報（preferredTransform）を使わないので横向きに読む（仕上げで回転する）。
10bit・HDR の HEVC も 8bit にして読む。撮影時刻は、時差の書かれた QuickTime の作成日時があるときだけ使う

## 15. v0.5.1（ドリズルの診断）

利用者の要望は「ざっくり効きそうかどうか、効くならざっくり何倍まで効きそうか」。スタックを2回して比べる検査（FRC）は
入れず、アライメントの結果（参照画像とAP×フレームの変位）だけから見積もる（`drizzle_diagnosis.hpp/.cpp`）。

- **像の細かさ**: 対象を囲む正方形（2の累乗・64〜1024）にハン窓を掛けた動径パワースペクトルで、信号がノイズの2倍まで
  落ちる周波数をナイキストを1として求める。**ノイズの水準は背景の空（対象の矩形の外）の、横に隣り合う画素の差の
  中央絶対偏差から**決め、σ²Σw² を床にする。空があれば斜めの最も細かい周期（1.4）まで測り、そこでも落ちきらなければ
  傾きで外挿して 2 で頭打ちにする（ナイキストより細かい周期は折り返して重なり、1枚の画像からは見分けられない）
- 最初は床を「2次元スペクトルの四隅の中央値」「最細のウェーブレット層の中央絶対偏差」としたが、どちらも信号を含んで
  しまい、粗く撮れた像ほど「等倍で十分」と誤る（1枚の画像では、ナイキスト近くまである細部と白色ノイズを区別できない）。
  空が写っていない（月面・太陽の全面）ときだけ四隅の中央値に戻し、控えめに見積もったことを画面に出す
- **位置のばらつき**: APごとに品質上位の採用フレームの変位の端数を、画素を 2×2・3×3 に分けた升目に数え、
  均等に分けたときの1/4以上入った升目の割合（APの中央値）。3×3の75%以上→3、2×2の75%以上→2、50%以上→1.5
- **採用枚数**: スタックと同じ数え方の APあたり採用枚数 k から √(k/5)（1画素あたり5枚ぶん以上）
- 3つの最小を 1 / 1.5 / 2 に丸めて答えにする
- 試験: 3倍細かい格子に、決まった周波数までの模様を円の中だけに描いて光学系と同じく帯域を切り、3×3画素ずつまとめ
  （本物の折り返しと空がある）、ノイズを足した画像で、細かく撮れた像（0.4）→1×、ナイキストの 0.8・1.2 → 測った値が
  ±0.1 以内、粗い像（2.5）→2×、位置が揃う・枚数が少ない → 1×、空が無い → 控えめ、を単体テストにした
- 実データ（採用30%）: 木星AVI 1.24（1×）、木星SER 1.26（1×）、月面SER 20枚（枚数で1×）、CR2 8枚（位置と枚数で1×）。
  手元の素材はどれも焦点距離が足りているか枚数が少なく、2× 以上は出ない
- GUI: ドリズル拡大欄に［ドリズルを診断］（APを使う方式でアライメントした後だけ押せる。裏で計算）、結果の文、
  見積もりに合わせるボタン。解析結果か採用率が変わったら結果を消す。タブの切り替え・見出しの開閉は欄の部品を直接
  隠すので、出し入れする結果の文は入れ物に包んだ。GUIの自己検証に「押せる・結果が出る・倍率を合わせる・採用率の変更で
  消える」を足した

既知の制限: 明るい対象ではショットノイズのぶん、空より像の上のほうがノイズが多いので、像の細かさはやや甘く出る。
参照画像は上位フレームの平均なので、ノイズは白色より細かい周期で少なく、こちらは控えめに働く。いずれも目安である。

## 16. リリース前の点検（2026-09-28）

### 行った検査
- **セキュリティ**（PCに致命的なことをしないか）: コマンドの実行・ネットワーク・ファイルの削除を全ソースで確認。
  削除はプリセットの削除（プリセットのフォルダの中だけ。名前の `/` `:` は置き換え、必ず `.json` を付ける）と、
  `scripts/build_app.sh` の `dist/LunaStack.app` だけ。書き出しは保存パネル経由、まとめて書き出しは上書きしない
- **警告・対応OS**: `-Wall -Wextra -Wunguarded-availability(-new)` で警告0（10.13にないAPIは元からエラー扱い）。
  配布版の最低OSは 10.13
- **静的解析**（`clang --analyze`、51ファイル）: 指摘6件はすべて実害なし（アプリ本体の delegate、使われない代入など）
- **AddressSanitizer＋UndefinedBehaviorSanitizer**: 単体テスト全件、CLIで SER（8/16bit・モノクロ・カラー・Bayer）・AVI・MP4・
  CR2・PNG/TIFF/FITS連番・サイドカーの再利用・ドリズル3×＋低メモリ・処理範囲・ダーク／フラットを通しで処理。
  GUIの自己検証（木星・月・CR2・MP4）
- **ThreadSanitizer**: 単体テスト全件、GUIの自己検証（木星・MP4）で警告0
- **リーク**（`leaks --atExit`、GUIの自己検証を最後まで）: 0件
- **壊れたファイル**（ファジング）: SER・AVI（非圧縮・MJPEG）・MP4/MOV・TIFF・PNG・FITS・JPEG・DNG の約2800通りと、RAW（DNG・CR2）
  675通り、サイドカー300通り。自前の読み込みで見つかったのは下のTIFFの1件だけ。LibRaw（同梱）の中の未定義動作
  （浮動小数点→整数の範囲外変換、負のシフト）は結果が不定になるだけでメモリの不正アクセスは無く、同梱物は変えない方針なので記録のみ
- **特殊な入力**: 1〜3フレーム、16×16・8×8、奇数寸法・奇数幅のBayer、真っ黒・飽和、端の処理範囲、開始＞終了の範囲などは、
  処理するか分かりやすいエラーで止まる。読み取り専用の場所の入力でも最後まで処理できる（サイドカーは保存されない）
- 修正前後で CLI の出力（16bit TIFF・仕上げ込みPNG・ドリズル2×のfloat TIFF・MP4からのFITS）がバイト単位で一致

### 直したもの
- **サイドカー**: 並びの長さを「ファイルの残り」と照らしてから確保し（以前は AP数×フレーム数で数十TBの確保になりえた）、
  寸法・フレーム番号・AP位置・変位・参照画像の値を検証する。回帰テストを追加
- **TIFF・PNGの読み込み**: 値の個数が0の欄で空の並びの先頭を読んでいた（ファジングで発見）。寸法（一辺10万・3億画素）・
  標本数・タイルの大きさに上限を設けた（数十バイトの壊れたファイルで数十GBを確保して0で埋めにいっていた）。回帰テストを追加
- **書き出し**: NaN の画素を16bitへ変換する未定義動作を直した（0にする）。4GBを超えるTIFFはファイル内の位置があふれて
  壊れたファイルを黙って書いていたので、FITSを勧めるエラーで止める
- **MOV・MP4**: デコーダを付けられない動画で AVFoundation の Objective-C 例外が出るとアプリごと落ちうるので、事前に確かめ、
  出た例外は C++ の例外に置き換える
- **設定のJSON**（プリセット・サイドカーの設定）: 数値の欄に配列・辞書・null があると Objective-C の例外で設定が途中までしか
  入らなかった。照合用の署名が無いサイドカーを信用していたのも直した
- CLI の版が 0.9.0 のままで、出力画像の作成ソフトの記録にも入っていた（プロジェクトの版から取るようにした）。テスト用の合成データの整数あふれ

### 既知の制限・未確認
- **Apple シリコン（arm64）では一度も実行していない**（開発機は Intel Core i9）。仕様書 §7.1 のとおり、実機での精度回帰テストが
  リリース条件。CPUの種類で分岐するコードは無い。積和演算（FMA）のため Intel と Apple シリコンで結果が最下位ビット程度違いうる
  （要件は同じマシンでの一致なので反しない）
- 木星では全フレームが「共通の位置ずれへ退避」になる。v0.2.3 で測定して決めた挙動（縞の偽相関で輪郭が歪むのを防ぐ）で、
  改善はAPごとのフレーム選別から来ている
- 品質評価の直後は、壊れたフレームが品質の上位に来てグラフの縦軸がつぶれる（アライメントで除外される）
- 読み取り専用の場所ではサイドカーを保存できないことが、画面には出ずログにだけ残る
- 点検中に開発機で自前ビルドの実行ファイルが起動しなくなった（lldb を打ち切ったあと。再起動で回復）。回復後に確かめたこと:
  型のおかしい設定のJSONでも例外なく開ける（サイドカーは捨てて品質評価の結果から再開）、署名の無いサイドカーを捨てる、
  フレーム範囲・処理範囲つきのサイドカーが検証を通って同じ結果を出す、配布版（universal）のテスト全件とGUIの自己検証（木星・CR2）
